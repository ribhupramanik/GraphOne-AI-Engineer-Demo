# GraphOne / FrontierAtlas | Three-page architecture brief

## 1. System design and horizontal scale

**Goals:** 500,000+ startup/product/paper entities; highly concurrent but source-friendly collection; independently verifiable provenance; idempotent distributed processing; near-real-time news and job signals; cost-controlled optional LLM extraction. Output schema is `schemaVersion: 1.0`, six-sheet export and mapping audit log. Baseline trial uses an asyncio HTTP client and transactional SQLite.

**Production pipeline:** source registry -> Scheduler (incremental cursors or snapshots) -> durable queue by source + identity -> Async HTTP / API workers (per-host token buckets, HTTP retry policies) -> immutable raw S3 objects and metadata checksum -> deterministic parser -> evidence-gated LLM enrichment -> normalizer / canonicalizer -> Postgres UPSERT + entity graph -> exporter / monitoring. Dead-letter queues retain irrecoverable parse and HTTP failures; no source item is treated as successful until the transaction commits. Partition entities by canonical source key; apply configurable resource pools, memory limits and workload pacing. Use object storage and queue fan-out to avoid Python process memory storing all 500k items. 500k is a capacity design goal, **not a volume claimed as executed in this trial**.

**Connectors:** YC company directory snapshot for startups; Hugging Face application spaces or authenticated Product Hunt API for products; historical PWC paper-code associations with arXiv Atom metadata and *live* GitHub `stargazers_count` for paper-backed repositories; 5 news feeds and 5 job boards. Each connector validates schema and preserves original source URL. For 1,000 papers require linked, live GitHub repo and arXiv title/author/published date; missing associations/metrics are missing, never zeros by assumption. A daily refresh updates stars separately, retaining observation timestamps.

**Concurrency limits:** asyncio global semaphore with source-specific concurrency pools and per-host pacing. Only raise rate after explicit permission / rate guidance; prioritise official APIs and feeds. When response is 401/403/anti-bot, stop that source rather than rotate identities or break challenges. Use approved integrations or licensed data for protected providers. No claims of guaranteed full HTML across blocked sites.

## 2. LLM resilience, freshness and distributed deduplication

**LLM chain:** Gemini Flash -> Groq GPT-OSS -> DeepSeek, enabled only when corresponding credentials exist. Extract only requested fields from current source text; force structured JSON with supporting verbatim evidence spans; discard fields whose evidence is absent in the captured source. First do a deterministic parse of exposed API fields to minimize LLM cost. Semantic chunking ranks high-value paragraphs (dates, repo links, product names, numbers), preserves original order, and caps request size. If 413 occurs, halve the character budget and retry same provider (max four shrinking attempts); then fallback. On 429/5xx/timeout use `Retry-After` (numeric or HTTP date) or bounded exponential backoff plus jitter. Respect provider-specific RPM/TPM token buckets and a circuit breaker; cap concurrency and spending. Do not repeat a nonidempotent LLM call indefinitely; enqueue failure for later review.

**Exactly-once effect:** Distinguish queue *at-least-once delivery* from effective exactly-once database writes. Compute canonical URL plus provider ID, content checksum and source publication version. Production Postgres has UNIQUE(record_type, canonical_key) and UNIQUE(canonical_url) on signal sightings; transactionally claim work via `FOR UPDATE SKIP LOCKED`, lease/fencing token, then UPSERT and commit. A worker crash causes safe retry with no duplicate exported row. Publish only committed event IDs. Retain mapping log with raw-to-canonical, method, confidence and provenance. SQLite demo uses these same uniqueness semantics on a single host.

**Strict 24-hour window:** Capture source `published_at` at ingestion time; accept only timezone-aware UTC interval `[now-24h, now]` (including start). Normalize RFC822, ISO8601, UTC epochs and relative forms when collection reference time is known. Prefer feed `pubDate` / Atom `published`; cross-check page metadata, JSON-LD or `<time>` if possible. `updated_at`, HTTP Last-Modified, first observed time and URL creation time are **not evidence** of publication time, so they can mark "new since last crawl" but cannot certify 24-hour freshness. Contradictory page/feed timestamps trigger rejection/review. Store `collectedAt` separately. Crawl near submission to avoid staleness of results already collected.

## 3. Storage, graph, safeguards and evaluation

**Storage rationale:** Postgres for relational consistency, partitioned normalized entities, canonical IDs, star metric time series, source snapshot pointers and ownership/foreign-key relationships. S3/compatible blob storage for raw HTML/JSON and immutable checksums to support replay and audit. Postgres pgvector for text embeddings, semantic retrieval and approximate candidates (a candidate is *never* automatically canonical without deterministic evidence). Neo4j or Postgres edge tables for startup -> product, person -> startup and paper -> repository relationships. Start with Postgres edge tables at lower complexity; adopt Neo4j if traversal latency and analytics justify operating a second database. Maintain separate materialized search tables.

**Resolution design:** Unicode normalization, legal-suffix removal, punctuation/space folding, exact alias table of 50+ well-known names, then conservative similarity threshold (>=0.93). For stronger production matches, verified website domain / registry IDs outrank name alone. Low-confidence entries remain unresolved; no fuzzy blind merges. Track alias provenance, canonical ID, version, score and human override. Product `startupName` is null when affiliation is unverified. Pricing is null when source does not publish a valid enum. This is preferable to hallucination.

**Operational guardrails:** Structured logs with source and attempt, tracing IDs, collection metrics, alerting on zero published signals, 429 rate, blocked sources, stale feed, failed full-text extraction, duplicate count and invalid values. Regular checkpoint snapshots + queue state to recover resumably. Replay raw evidence on parser upgrades. Robots/ToS compliance and consent for API access. For Cloudflare / Datadome / captcha: observe the block, request an approved API/partner feed or human permission, use caching and rational pacing, never circumvent protective controls.

**Acceptance checks:** 1,000 real unique rows each for startups/products/papers, strict live GitHub stars and arXiv metadata, fresh signals from five attempted sources each, six tab names exactly, source URLs for each entity, source-level failure disclosures, GitHub repo with source/test/README, and 3-page PDF. Missing count targets are explicit defects, **not concealed by mock rows**. "Fresh" means actual 24h publication with evidence; records lacking valid dates are quarantined.
